**Findings**

1. Critical: the spec’s initial-load contract is not supported by the current API usage. It assumes one call returns all projects and all active tasks for global filters, counts, the summary table, and `?id=` selection, but the current endpoints are paginated and the current client calls only the first page (`projects`: default 50, `tasks`: default 100, both capped). That will miscount attention cards, create false “No tasks” matches, and make some projects impossible to select from the initial dataset. Refs: [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L157), [apiClient](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/lib/apiClient.js#L25), [projects route](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/app/api/projects/route.js#L58), [tasks route](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/app/api/tasks/route.js#L54)

2. Critical: the spec calls the notes API incorrectly. It says `apiClient.getNotes({ projectId })`, but the current singleton client signature is positional (`getNotes(projectId, taskId)`) and returns the raw JSON wrapper, not an array. A literal implementation of the spec will not load project notes. Refs: [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L150), [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L164), [apiClient](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/lib/apiClient.js#L169), [useApiClient](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/hooks/useApiClient.js#L108)

3. High: the desktop path back to the “no project selected” dashboard is missing. The spec defines the dashboard as a first-class state and adds a mobile-only back button, but it never defines how desktop users clear a selection other than filtering the selected project away. It also does not say whether clearing selection removes `?id=`. Refs: [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L80), [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L181), [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L229)

4. High: deep-link behavior is underspecified and not guaranteed by the current API surface. There is no `GET /api/projects/[id]`, so a bookmarked `?id=` depends entirely on the initial list containing that project. The spec does not define what happens when the id is invalid, completed while `showCompleted` is off, filtered out by area/pill, or simply outside the first page. Refs: [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L179), [projects id route](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/app/api/projects/%5Bid%5D/route.js#L34)

5. High: the redesign drops existing project-deletion and unassigned-task behavior without replacing it. The current page and drawer both support delete, and the current schema leaves tasks unassigned on project delete. The spec removes the drawer and never says where delete lives or how orphaned tasks are surfaced, even though the current page has an explicit unassigned section. Refs: [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L221), [ProjectsView](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/components/Projects/ProjectsView.jsx#L425), [ProjectDetailDrawer](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/components/Projects/ProjectDetailDrawer.jsx#L562), [task migration](/Users/peterpitcher/Cursor/OJ-Planner2.0/supabase/migrations/20260404000001_prioritisation_replacement.sql#L41), [ProjectsView](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/components/Projects/ProjectsView.jsx#L829)

6. High: dashboard/filter semantics are incomplete and can produce conflicting implementations. The spec does not fully define whether attention cards and the summary table respect the active pill, `showCompleted`, and area filter together; whether “Overdue” counts unique projects or double-counts “project overdue” plus “has overdue task”; or whether completed/cancelled projects can appear in attention filters when `showCompleted=true`. Refs: [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L44), [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L84), [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L96), [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L189)

7. Medium: the area dropdown contract conflicts with the current endpoint and data normalization. The spec says “distinct area from the user’s projects,” but `/api/areas` currently mixes task and project areas and preserves original casing. With exact string comparison in the spec, case/whitespace variants can create empty filters or hide matching projects. Refs: [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L46), [areas route](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/app/api/areas/route.js#L18), [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L194)

8. Medium: the “reuse as-is” claims are inaccurate. `TaskCard` depends on `useSortable`, so it needs a `DndContext`/`SortableContext` wrapper even when drag-and-drop is out of scope, and it still shows a drag handle. `AddTaskInput` is not a standalone component at all; it is private inside `ProjectsView.jsx`, so it cannot be reused without refactoring. Refs: [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L215), [TaskCard](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/components/shared/TaskCard.jsx#L162), [ProjectsView](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/components/Projects/ProjectsView.jsx#L179), [ProjectsView](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/components/Projects/ProjectsView.jsx#L127)

9. Medium: date logic is underdefined and conflicts with existing utilities. The spec uses raw `today` and `differenceInCalendarDays` rules for overdue/stale detection, but the codebase already has a London-aware helper specifically to avoid timezone and DST boundary bugs. The spec should pick one timezone/date-normalization rule. Refs: [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L39), [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L199), [dateUtils](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/lib/dateUtils.js#L132)

10. Medium: freshness/editability rules are incomplete. The spec bases “Stale” on `updated_at`, but note creation does not touch project `updated_at`, so a project can remain stale immediately after adding notes unless that is intended. It also says all header fields are editable inline without defining whether completed/cancelled projects remain editable and whether adding tasks/notes is allowed in those states. Refs: [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L110), [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L201), [notes route](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/app/api/notes/route.js#L63)

11. Medium: mutation requirements are incomplete for derived UI. The spec says areas are fetched once on initial load and describes sidebar count updates, but it does not require recomputing attention cards, summary-table rows, or area options after project/task mutations. Creating or editing a project with a new area will stale the dropdown unless that refetch is specified. Refs: [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L157), [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L168), [areas route](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/app/api/areas/route.js#L5)

12. Low: smaller gaps remain. The spec does not define attention-dot precedence when a project is overdue, stale, and empty at once; whether every “tasks” count is active-only or total; how a user clears an existing project due date in the new inline picker; or how the main-panel scroll rules interact with “both columns scroll independently.” Refs: [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L64), [spec](/Users/peterpitcher/Cursor/OJ-Planner2.0/docs/superpowers/specs/2026-04-07-projects-page-redesign-design.md#L114), [ProjectDetailDrawer](/Users/peterpitcher/Cursor/OJ-Planner2.0/src/components/Projects/ProjectDetailDrawer.jsx#L421)

Core schema support is mostly present: `projects` already has `name`, `description`, `status`, `due_date`, `stakeholders`, `area`, `updated_at`; `tasks` already has state-based workflow and nullable `project_id`; `notes` already supports `project_id`. The gaps are mostly API contract, pagination, normalization, and behavior-definition issues rather than missing columns.

**Open Questions**

- Should attention cards and the summary table respect the active pill and `showCompleted`, or only the area filter?
- What is the desktop action to clear selection and return to the dashboard, and should that clear `?id=`?
- Should completed/cancelled projects be editable and allow new tasks/notes?
- Should note creation update `projects.updated_at` and clear “Stale”?
- Is project deletion still in scope, and if so where do unassigned tasks surface afterward?
